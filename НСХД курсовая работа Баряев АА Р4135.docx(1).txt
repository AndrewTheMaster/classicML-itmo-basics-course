ВВЕДЕНИЕ
В современном мире распределённые системы играют ключевую роль в обеспечении высокой доступности и отказоустойчивости сервисов. Одной из основных проблем распределённых систем является достижение консенсуса между узлами кластера при наличии сетевых разделений и отказов узлов.
Алгоритм Raft был разработан как альтернатива алгоритму Paxos, предоставляя более понятную и реализуемую модель консенсуса. Raft разделяет проблему консенсуса на три независимые подзадачи:
- Выбор лидера (Leader Election)
- Репликация лога (Log Replication)
- Безопасность (Safety)
Цель работы: Практика по разработке распределённой системы, требующей консенсуса на основании алгоритма Raft.
Задачи:
1. Разработать распределённое отказоустойчивое Key-Value хранилище
2. Реализовать алгоритм Raft для обеспечения консенсуса
3. Обеспечить восстановление системы в случае гибели узлов без потери данных
4. Провести тестирование и исследование поведения системы
5. Определить условия стабильного перевыбора лидера и границы восстановления кластера

1 Постановка задачи
1.1 Требования к системе
Система должна обеспечивать:
1. Отказоустойчивость:
   - Автоматическое восстановление при отказе узлов
   - Сохранение данных при перезапуске узлов
   - Продолжение работы при потере части узлов (при наличии quorum)
2. Консистентность:
   - Все узлы должны иметь согласованное состояние
   - Записи должны быть реплицированы на все доступные узлы
   - Гарантия линейной консистентности (linearizability)
3. Доступность:
   - Система должна оставаться доступной при наличии quorum
   - Чтение данных должно быть возможно с любого узла
   - Запись данных должна проходить через лидера
1.2 Технические требования
- Язык программирования: Go
- Контейнеризация: Docker
- Протокол коммуникации: HTTP REST API
- Алгоритм консенсуса: Raft
2 Обзор алгоритма Raft
2.1 Основные понятия
Raft - это алгоритм консенсуса для управления реплицированным логом. Ключевые концепции:
- Лидер (Leader): единственный узел, который обрабатывает все запросы на изменение
- Фолловер (Follower): пассивные узлы, которые получают обновления от лидера
- Кандидат (Candidate): узел, который пытается стать лидером
- Терм (Term): логическое время в Raft, увеличивается при каждой попытке выборов
2.2 Механизм выбора лидера
Рисунок 1: Диаграмма состояний узла в Raft
  

Процесс выбора лидера:
1. Узел начинает как Follower
2. При отсутствии heartbeat от лидера, узел переходит в Candidate
3. Candidate отправляет запросы на голосование (RequestVote)
4. При получении большинства голосов, Candidate становится Leader
5. Leader отправляет heartbeat всем Followers
2.3 Репликация лога
Рисунок 2: Схема репликации лога в Raft
  

Процесс репликации:
1. Клиент отправляет запрос на запись лидеру
2. Лидер добавляет запись в свой лог
3. Лидер отправляет AppendEntries всем фолловерам
4. После получения подтверждения от большинства, запись коммитится
5. Запись применяется к состоянию на всех узлах
2.4 Quorum и безопасность
Quorum (кворум) - это минимальное количество узлов, необходимое для принятия решений. Для кластера из N узлов:
Quorum = [N/2] + 1
Примеры:
- 3 узла: quorum = 2
- 5 узлов: quorum = 3
- 7 узлов: quorum = 4
Без quorum система не может:
- Выбрать нового лидера
- Принять новые записи
- Гарантировать консистентность

3.2 Компоненты системы
3.2.1 LSM-Tree Storage Engine
Memtable - отсортированная структура данных в памяти для быстрой записи:
- Использует бинарный поиск для вставки
- При достижении порога размера сбрасывается на диск
- Потокобезопасна (использует mutex)
WAL (Write-Ahead Log) - журнал предварительной записи:
- Все операции записи сначала логируются в WAL
- Обеспечивает долговечность данных
- При перезапуске узла WAL воспроизводится для восстановления состояния
SSTables - неизменяемые отсортированные таблицы на диске:
- Организованы по уровням (L0, L1, L2...)
- Используют Bloom фильтры для быстрого поиска
- Поддерживают кэширование блоков
Compaction - процесс слияния SSTables:
- Уменьшает количество файлов
- Удаляет устаревшие записи
- Оптимизирует производительность чтения
3.2.2 Raft Consensus Layer
Raft Node (`pkg/raftadapter/node.go`):
- Интеграция с библиотекой `go.etcd.io/etcd/raft/v3`
- Управление жизненным циклом Raft узла
- Обработка команд и применение к хранилищу
Transport (`pkg/raftadapter/transport.go`):
- HTTP транспорт для Raft сообщений
- Retry логика для сетевых ошибок
- Таймауты и обработка недоступных узлов
Key Features:
- `CheckQuorum: true` - проверка наличия quorum
- `PreVote: true` - предотвращение ненужных выборов
- ElectionTick: 10, HeartbeatTick: 1
3.2.3 Sharding & Routing
Consistent Hashing (`pkg/cluster/ring.go`):
- Распределение ключей по узлам
- Виртуальные ноды для балансировки нагрузки
- Минимальная миграция при изменении топологии
Router (`pkg/cluster/router.go`):
- Определение владельца ключа через hash ring
- Маршрутизация запросов на локальный или удалённый узел
- Поддержка replication factor для репликации данных
3.2.4 HTTP API
Endpoints:
- `PUT /api/string` - запись ключа-значения
- `GET /api/string?key=...` - чтение значения
- `DELETE /api?key=...` - удаление ключа
- `GET /health` - проверка здоровья узла
- `POST /api/internal/raft` - внутренний endpoint для Raft сообщений
Redirect механизм:
- Фолловеры возвращают `307 Temporary Redirect` с адресом лидера
- Клиент автоматически следует редиректу

4.2 Обработка запросов на запись
Рисунок 5: Поток обработки PUT запроса
  

Процесс обработки PUT:
1. HTTP сервер получает запрос
2. Проверка: является ли узел лидером?
   - Если нет → редирект на лидера (307)
   - Если да → продолжение
3. Router определяет shard для ключа
4. Создание команды Raft:
cmd := raftadapter.NewCmd(store.InsertOp, []byte(key), []byte(value))
5. Выполнение через Raft:
err := s.node.Execute(r.Context(), cmd)
6. Raft реплицирует на фолловеров
7. После commit, команда применяется к Store на всех узлах
4.3 Выбор лидера
Реализация использует библиотеку etcd/raft, которая автоматически:
- Отслеживает heartbeat от лидера
- Инициирует выборы при timeout
- Обрабатывает голосование
Ключевой код в `pkg/raftadapter/node.go`:
func (n *Node) Run(ctx context.Context) error {
    ticker := time.NewTicker(n.tickInterval) // 100ms
    for {
        case <-ticker.C:
            n.underlying.Tick() // Raft tick
        case rd := <-n.underlying.Ready():
            n.handleReady(rd) // Обработка событий Raft
    }
}
4.4 Восстановление после перезапуска
При перезапуске узла:
1. WAL Replay:
func (s *Store) restoreFromJournal() error {
    return s.jr.Replay(s.seqN.Val()+1, func(entry wal.Entry) error {
        return s.mt.Upsert(entry.Key, entry.Value, entry.SeqNum, entry.Meta)
    })
}
2. Raft Catch-up:
   - Узел подключается к кластеру
   - Получает последние записи от лидера
   - Применяет их к своему состоянию
3. Синхронизация:
   - Узел догоняет текущее состояние кластера
   - Становится полноценным участником

Условия стабильного перевыбора лидера
Стабильный перевыбор происходит когда:
- Доступно большинство узлов (quorum)
- Сетевая связность между узлами стабильна
- Election timeout достигается (обычно 1-2 секунды)
Перевыбор НЕ происходит когда:
- Меньше quorum узлов доступно
- Сетевое разделение изолирует узлы
- Все узлы недоступны одновременно
Границы восстановления кластера
Кластер МОЖЕТ восстановиться:
- При восстановлении quorum (узлы возвращаются онлайн)
- При заживлении сетевых разделений
- При перезапуске всех узлов
Кластер НЕ МОЖЕТ восстановиться автоматически:
- При постоянной потере quorum
- При split-brain с равными группами
- Требует ручного вмешательства для восстановления
Ограничения и будущие улучшения
Текущие ограничения:
1. Raft log хранится в памяти (MemoryStorage) - для production нужна персистентность
2. Нет динамического добавления/удаления узлов (требует перезапуска)
3. Ограниченное нагрузочное тестирование
Возможные улучшения:

#!/usr/bin/env bash
set -euo pipefail
# Определение лидера по HTTP статусам
detect_leader() {
  local tries="${1:-30}"
  for _ in $(seq 1 "$tries"); do
    for u in "${NODES[@]}"; do
      code=$(curl -s -o /dev/null -w "%{http_code}" \
        --connect-timeout 1 --max-time 2 \
        -X PUT "$u/api/string" -d "key=__probe__&value=1" 2>/dev/null || echo "000")
      if [[ "$code" == "200" ]]; then
        echo "$u"
        return 0
      fi
    done
    sleep 0.5
  done
  return 1
}

func (s *Server) handlePut(w http.ResponseWriter, r *http.Request) {
    // Редирект на лидера, если текущий узел не лидер
    if redirected, err := s.redirectLeader(w, r); redirected || err != nil {
        if err != nil {
            slog.Error("Failed to redirect to leader", "error", err)
        }
        return
    }
    // Парсинг формы
    if err := r.ParseForm(); err != nil {
        s.writeJSON(w, http.StatusBadRequest, NewErrorResponse("Failed to parse form"))
        return
    }
    key := r.FormValue("key")
    value := r.FormValue("value")
    if key == "" || value == "" {
        s.writeJSON(w, http.StatusBadRequest, NewErrorResponse("Missing key or value"))
        return
    }
    // Создание Raft команды
    cmd := raftadapter.NewCmd(store.InsertOp, []byte(key), []byte(value))
    // Выполнение через Raft (репликация на все узлы)
    if err := s.node.Execute(r.Context(), cmd); err != nil {
        s.writeJSON(w, http.StatusInternalServerError, NewErrorResponse(err.Error()))
        return
    }
    s.writeJSON(w, http.StatusOK, NewSuccessResponse())
}
Приложение F: Код выполнения Raft команды
Файл: `pkg/raftadapter/node.go`
func (n *Node) Execute(ctx context.Context, cmd Cmd) error {
    // Сериализация команды
    data, err := json.Marshal(cmd)
    if err != nil {
        return fmt.Errorf("marshal command: %w", err)
    }
    // Валидация команды
    if err := n.validateCommand(cmd); err != nil {
        return err
    }
    // Создание канала для результата
    resultChan := make(chan proposeResult, 1)
    // Регистрация команды
    n.proposalsMu.Lock()
    n.proposals[cmd.ID] = resultChan
    n.proposalsMu.Unlock()
    defer func() {
        n.proposalsMu.Lock()
        delete(n.proposals, cmd.ID)
        n.proposalsMu.Unlock()
    }()
    // Предложение команды в Raft
    if err := n.underlying.Propose(ctx, data); err != nil {
        return fmt.Errorf("propose: %w", err)
    }
    // Ожидание результата (commit или timeout)
    select {
    case result := <-resultChan:
        return result.Err
    case <-ctx.Done():
        return ctx.Err()
    }
}
